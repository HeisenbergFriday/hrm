### 2026-08-18 P1 Go 1.26.5 标准库漏洞阻塞发布

| 字段 | 内容 |
|---|---|
| 日期 | 2026-08-18 |
| 级别 | P1 |
| 模块/标签 | `go` `security` `govulncheck` `ci` `docker` `release` |
| 范围 | Go 工具链版本、GitHub CI 漏洞扫描、生产后端构建镜像 |
| 现象 | 兼职考勤修复的 Go/Python/前端测试均通过，但 GitHub Backend job 在 `govulncheck` 阶段失败，报告 6 个业务调用链可达的 Go 标准库漏洞，阻止受保护的 `master` 合并。 |
| 根因 | `go.mod` 和 Dockerfile 均固定在 Go 1.26.5；`actions/setup-go` 从 `go.mod` 选择相同旧版本，CI 与生产二进制都会链接存在漏洞的标准库。6 个漏洞统一修复于 Go 1.26.6。 |
| 修复 | 将 `go.mod` 最低版本和 Dockerfile 后端 builder 镜像同步升级到 Go 1.26.6；CI 继续通过 `go-version-file: go.mod` 自动使用同一修复版本。 |
| 验证 | Go 自动下载 1.26.6 后，`go test ./...`、`go vet ./...`、`golangci-lint run` 全部通过；`go run golang.org/x/vuln/cmd/govulncheck@latest ./...` 报告 `0 vulnerabilities`。Docker backend-builder 构建因本机 Docker Desktop daemon 未启动而未执行，发布镜像可构建性待 GitHub/发布流水线验证。 |
| 防复发 | 1. 标准库漏洞修复必须升级 Go 工具链，不能通过忽略 `govulncheck` 或改调用点掩盖。<br>2. `go.mod`、CI setup-go 和 Docker builder 必须使用同一修复版本；CI 从 `go.mod` 读取时仍需核对 Dockerfile。<br>3. 合并发布前以调用链可达漏洞为门槛；仅“模块存在但代码不可达”的告警可按扫描器结论另行评估。 |
| 状态 | fixed（版本声明和本地扫描已验证，待 GitHub CI 与后端镜像构建验证） |

| 字段 | 内容 |
|---|---|
| 日期 | 2026-08-18 |
| 级别 | P1 |
| 模块/标签 | `attendance-toolbox` `parttime` `status-mapping` `roster` `intern` |
| 范围 | 兼职模块月度打卡明细生成（钉钉记录聚合 → Go 匹配 → Python Excel 渲染） |
| 现象 | 需求方查看兼职模块时，实习生前段日期出现一片空白，只有少数有打卡时间的日期显示状态；实习生职位在导出中还可能被默认成“兼职”。 |
| 根因 | Go 的 `statusLabel` 只有存在上班或下班时间才输出状态，钉钉返回但没有打卡时间的 `NotSigned`、`Absenteeism/Absent`、`SeriousLate` 被静默丢弃；`MatchParttimeMonthlyPunch` 标准化 roster 时只复制工号、姓名、UserID，丢失 `Position`、`Department`，Python 因此无法识别实习生身份。 |
| 修复 | 异常状态先于打卡时间判断，统一兼容大小写、下划线和连字符变体并输出“缺卡/旷工/严重迟到”（存在时间时附带时间）；标准化 roster 保留职位和部门字段。没有任何源记录的日期继续留空，不按工作日或实习生身份臆造出勤。 |
| 验证 | 新增 Go 回归覆盖三类无时间异常状态及 `Serious_Late` 变体，覆盖实习生职位/部门在匹配后的保留；兼职月度 Go/Python 定向测试、后端全量测试、`go vet`、`golangci-lint` 和 `git diff --check` 通过。 |
| 防复发 | 1. 第三方考勤状态必须先做规范化映射，再决定是否依赖打卡时间；未知状态不得被静默当作空白。<br>2. roster 标准化必须保留下游筛选和导出所需的身份字段（至少工号、姓名、职位、部门）。<br>3. “明确异常状态”与“完全没有源记录”必须区分；后者需结合排班规则处理，禁止直接补成出勤。<br>4. 回归测试必须覆盖异常状态无时间、状态命名变体和实习生身份字段。 |
| 状态 | fixed（代码与自动化验证完成，待部署后用真实实习生月份重新导出验收） |

### 2026-08-18 P1 组织同步运维工具误跑启动迁移与种子

| 字段 | 内容 |
|---|---|
| 日期 | 2026-08-18 |
| 级别 | P1 |
| 模块/标签 | `org-sync` `ops-tool` `database-migration` `seed` `read-only` `logging` `deploy` |
| 范围 | 镜像内 `sync_org_data` 运维工具 / 数据库初始化 / 定时组织同步 |
| 现象 | 部署后执行只读命令 `/app/sync_org_data -list-orgs` 时，工具先运行应用完整数据库初始化，触发启动迁移、兼容更新和种子检查，并在切换静默 logger 之前输出大量 SQL 及部分用户标识。虽未执行 `-confirm-sync`，但只读命令已经越过预期的无写入边界，因此每天零点的自动同步不能安全启用。 |
| 根因 | 运维工具直接复用了面向应用启动的 `database.Init()`；该入口同时承担连接失败后建库、迁移、seed 和兼容数据更新。工具在完整初始化返回后才给 `database.DB` 替换静默 logger，无法阻止初始化阶段的 SQL 输出。数据库连接与应用启动副作用没有拆分。 |
| 修复 | 新增 `database.InitOperational()`：要求已有 `DATABASE_URL`，在连接前使用静默 GORM logger，只连接并 Ping 现有数据库，注册租户回调，不建库、不迁移、不 seed，连接失败时不替换全局 DB 句柄并直接返回错误。`sync_org_data` 所有模式统一改用该入口；同步与人数诊断改为先校验显式非空 `-org`，禁止把缺失值归一为 `default`。增加运行时测试验证不建表/不 seed、失败保留原句柄和租户回调，并增加 AST 回归测试禁止工具重新调用 `database.Init()`。 |
| 验证 | `go test ./internal/database -run 'TestInitOperational' -count=1`、`go test ./tools/ops/sync_org_data -count=1`、`go vet ./internal/database ./tools/ops/sync_org_data`、`go build ./tools/ops/sync_org_data` 通过；工具测试覆盖缺失组织 fail-closed 与显式组织透传。待重新部署后验证 `-list-orgs` 标准输出仅含 JSON，且不出现迁移、SQL、DSN 或用户标识。 |
| 防复发 | 1. 应用完整启动初始化与运维工具数据库连接必须使用不同入口。<br>2. 只读或定向运维工具禁止隐式建库、DDL、迁移、seed 和兼容数据更新。<br>3. SQL 静默 logger 必须在 `gorm.Open` 前配置，禁止连接后再替换。<br>4. 连接缺失或失败必须 fail-closed，不得尝试建库或继续业务操作。<br>5. 需要组织作用域的运维模式必须先校验显式非空 org，禁止把空值归一为 `default`。<br>6. 工具回归测试必须明确禁止 `database.Init()`，并验证租户回调仍注册。 |
| 状态 | fixed（代码与定向测试完成，待重新部署和容器内验收） |

| 验证 | `go vet ./internal/service/...` 通过；修改文件 `gofmt` 通过；编译通过。 |
| 防复发 | 1. 所有涉及外部网络或大数据量循环的长任务，必须在循环内显式检查 `ctx.Err()`。<br>2. 超过网关/HTTP 超时的同步任务必须改为异步执行（短请求创建任务 + 后台执行 + 轮询状态）。<br>3. 锁 TTL 必须小于任务预期最大执行时间，或改用心跳续期机制。 |
