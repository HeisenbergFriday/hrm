## 1. 背景与现状

### 1.1 两套系统的本质差异

| 维度 | D:\app（Python/Streamlit） | HR（Go/React） |
|---|---|---|
| 数据来源 | 人工上传 Excel（作息表/考勤表/签到表/花名册） | 钉钉 API 实时同步入库 |
| 计算触发 | 上传后即时计算，导出 Excel | 定时/手动任务，写回 DB |
| 作息识别 | 读 Excel **单元格颜色**（红=法定节假日、蓝=福利假） | `StatutoryHoliday` / `WeekScheduleRule` 表 |
| 输出 | 下载 Excel | 页面展示 + 导出 |

**核心洞察**：D:\app 约 1.1 万行里，相当比例是"解析 Excel 脏活"（表头识别、颜色解析、日期单元格兼容、姓名规范化）。这部分在 HR 中**不需要**，因为数据来自钉钉结构化 API。真正有价值、需要迁移的是**纯业务计算规则**。

### 1.2 D:\app 模块依赖关系

```
作息表 ──┬─→ calc_leave(请假) ────────┐  ← 整条链的地基，被 finally/parttime import
考勤表 ──┼─→ overtime(加班) ──────────┤
签到表 ──┴─→ subsidy(补贴扣款) ────────┼─→ calc_finally(最终结算 50 列)
兼职考勤 ─────→ parttime(兼职汇总) ─────┘（独立支线）
```

### 1.3 HR 后端现有覆盖度

| D:\app 模块 | 行数 | HR 现状 | 覆盖度 |
|---|---|---|---|
| leave/calc_leave | 1709 | `annual_leave_service.go` / `leave_handlers.go`（年假额度、调休台账） | 部分（架构不同） |
| overtime | 3417 | `overtime_matching_service.go`（基于 DB 已审批加班匹配） | 部分（架构不同） |
| subsidy | 2136 | 无 | **缺** |
| finally/calc_finally | 2072 | 无 | **缺** |
| parttime | 1687 | 无 | **缺** |

## 2. 方案总原则

1. **不整体移植、不逐行翻译**。只迁移 HR 缺失且业务仍需要的"计算规则内核"。
2. **数据双通道**：优先用钉钉同步数据（考勤 `Attendance`、员工 `User`/`EmployeeProfile`、作息 `WeekScheduleRule`/`StatutoryHoliday`）；对钉钉拿不到的字段（工资、银行卡、身份证、部门特例名单）保留**手动上传 Excel**补齐通道。
3. **硬编码业务规则显式化**：D:\app 里散落的部门关键字、人名/工号白名单、活动剔除规则，统一抽成**可配置项**（DB 配置表或配置文件），不再硬编码进代码。
4. **先补最缺、依赖最少的**，不三个一起上。

## 3. 数据来源映射（钉钉同步 vs 需上传）

### 3.1 可从钉钉同步数据直接获得
- 员工基本信息：工号、姓名、部门、岗位、入职/转正日期 → `User` + `EmployeeProfile`
- 每日打卡时间 → `Attendance`（CheckTime/CheckType）
- 应出勤/法定节假日/福利假 → `StatutoryHoliday` + `WeekScheduleRule`/`WeekScheduleOverride`
- 异动/离职日期 → `EmployeeTransfer` / `EmployeeResignation`
- 加班（已审批）→ `overtime_matching` 结果

### 3.2 钉钉拿不到、必须保留上传的字段
| 字段类 | 来源 | 说明 |
|---|---|---|
| 薪资类（基本工资/绩效/津贴/工资总额/缺勤扣款） | 上传花名册 | 敏感，透传不计算 |
| 银行卡/开户行/身份证/手机号 | 上传花名册 | 敏感，透传不计算 |
| 现有补贴扣款源表（迟到/早退扣款） | 上传（钉钉导出） | subsidy 的迟到早退扣款沿用源表 |
| 签到表（羽毛球等活动） | 上传 | 用于剔除 22:00 后打卡的晚走补贴 |
| 兼职月度汇总/兼职排班 | 上传 | 兼职考勤钉钉结构差异大 |

> 结论：**最终结算表的薪资/证件列本就不参与计算，是"保留透传列"**——这类信息永远走上传，不进钉钉同步，也符合安全要求。

## 4. 分模块迁移设计

### 4.1 补贴扣款（subsidy）— 建议**第一优先**
- **为什么先做**：HR 完全缺失；依赖最少（只需考勤打卡时间 + 签到表 + 现有补贴源表）；不被其他模块依赖。
- **计算内核**：
  - 迟到/早退扣款：沿用上传源表（不重算）
  - 旷工天数、缺卡次数：按 `Attendance` 打卡记录重算
  - 晚走补贴：考勤打卡；剔除签到表标记"已参加"活动当日 22:00 后打卡者
  - 产研休息日加班补贴：按部门关键字 + 作息（避开法定节假日）
- **需配置化**：`RD_DEPT_KEYWORDS`（产研部门）、`VALID_EMP_NO_PREFIXES`（工号前缀白名单）、活动剔除规则
- **数据通道**：考勤走钉钉同步；补贴源表 + 签到表走上传
- **产出**：`subsidy_service.go` + 上传/计算/导出 handler + 前端页面

### 4.2 兼职汇总（parttime）— 建议第二优先
- **为什么第二**：独立支线，不阻塞最终结算；但兼职考勤源结构复杂（北京环球/南京地铁/长沙安检等多套排班），钉钉覆盖弱。
- **计算内核**：多份月度汇总合并、按考勤组/部门/工号筛选兼职实习、工时/迟到早退/加班解析、480 分钟工作日 + 120 分钟月度豁免
- **数据通道**：以**上传为主**（钉钉难覆盖兼职多来源排班）
- **产出**：`parttime_service.go` + 上传/计算/导出 + 前端页面

### 4.3 最终结算（calc_finally）— 建议**最后做**
- **为什么最后**：50 列输出，依赖前面所有模块（请假/加班/补贴）的产出，是"总装车间"。前置模块没对齐前做它=空中楼阁。
- **计算内核**：汇总花名册 + 异动 + 作息 + 请假 + 加班 + 补贴 → 应出勤/计薪出勤/实际出勤、各类假期天数、旷工、入离职缺勤、当月转正天数、2倍/3倍加班（小时+天）
- **保留透传列**：薪资 15 列、银行卡/证件 6 列（走上传，不计算）
- **特例**：固定 4 天月休名单、休息日加班排除名单、成都工作地、运营支持人员判定 → 全部配置化
- **数据通道**：员工/考勤/作息/异动走钉钉；薪资证件走上传
- **产出**：`final_settlement_service.go` + 组装 handler + 前端汇总页 + Excel 导出

### 4.4 请假/加班（HR 已有）— 对齐而非重写
- 不重写。核对 D:\app 的请假类型口径（年假/调休/婚假/陪产假/丧假/产检假/工伤假/产假/病假/事假）、自然日 vs 应出勤日算法，与 HR 现有实现的差异，列差异清单后再决定是否补齐。

## 6. 风险与注意事项

1. **计算口径回归**：迁移后必须用**同一份历史数据**跑 Python 版和 Go 版，逐字段对账，容忍误差为 0（金额/天数）。这是验收硬门槛。
2. **敏感字段**：薪资、银行卡、身份证只透传不落计算逻辑；上传文件需限制权限、用后清理，遵守 CLAUDE.md 安全规则。
3. **硬编码特例**：D:\app 里的人名/工号/部门名单是真实业务特例，迁移时必须配置化并请业务方确认最新名单，不能照抄旧值。
4. **作息颜色语义**：Python 靠单元格颜色（红=法定节假日 FFFF0000、蓝=福利假 FF0070C0）识别，HR 改用 `StatutoryHoliday` 表——需确认表数据完整覆盖这些日期。
5. **工作量**：三块合计 Python 约 6000 行（去掉 Excel 脏活后核心规则预计 Go 2000~3000 行），非小工程，建议按里程碑分批。
