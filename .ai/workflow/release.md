# 阶段五：审查与发布

## 步骤 14：代码审查

测试后检查实际 diff，而不是仅根据计划或口头说明判断。

### 后端

- 参数验证和错误格式；
- 租户隔离、权限和越权；
- 事务、锁、幂等、并发和 context；
- SQL、索引、N+1 和迁移兼容；
- 外部调用失败、部分成功和终态；
- 未处理错误、硬编码、调试输出和安全问题。

### 前端

- TypeScript 类型和 API 契约；
- antd、设计规范和无障碍；
- Loading、空态、错误态和权限态；
- 请求竞态、重复点击、缓存和跨用户/跨组织泄漏；
- XSS、不安全内容、调试输出和无效重渲染。

### 通用

- 是否满足原始需求和验收标准；
- 是否有计划外修改；
- 测试是否覆盖关键风险；
- 文档和长期知识是否需要更新。

安全、逻辑和数据完整性问题必须修复。审查结论为：通过、需要修改或证据不足。

## 步骤 15：发布检查与部署

只在准备上线时执行：

- lint、测试、构建和审查已通过；
- 核心、边界和异常流程已覆盖；
- 数据库迁移、兼容和回滚已准备；
- 环境变量、依赖和配置已核对；
- API、用户和技术文档已更新；
- 日志、监控、告警和冒烟方案已明确。

### 发布策略

| 类型 | 策略 |
|---|---|
| 新功能 | 灰度后全量 |
| Bug 修复 | 验证通过后直接发布 |
| 数据库变更 | 兼容代码/迁移/切换分步发布 |
| 紧急修复 | 缩短流程但保留验证，事后补齐复盘 |

部署、推送、合并、迁移和外部消息都属于状态变更，必须在用户授权范围内执行。部署后做冒烟测试并观察日志/指标；失败时按预先方案回滚。
