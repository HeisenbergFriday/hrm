# 阶段四：测试

## 步骤 10：测试计划

新功能、复杂 Bug 和跨模块功能必须说明：

- 测试范围：功能、接口、兼容、权限、性能（如需要）；
- 测试策略：单元、集成、E2E、手动；
- 环境与依赖；
- 准入和准出标准；
- 阻塞条件。

简单文档、样式细节和配置说明可跳过正式测试计划，但仍需验证。

## 步骤 11：测试用例设计

新增业务逻辑、复杂分支、状态流转、金额/数量、权限或并发逻辑，在编码前覆盖：

```text
正常流程：输入/操作/预期
边界：空值、0、1、最大值、跨日/月/年、大数据量
异常：网络、数据不存在、重复提交、并发、权限不足
状态流转：合法路径、逆向路径、非法操作
多租户：当前组织、跨组织、缺少 org
```

禁止只测正常流程。

## 步骤 12：执行与验证

代码修改后必须运行与修改范围匹配的验证。

### 基础验证

```bash
# 后端
go fmt ./...
go vet ./...
golangci-lint run

# 前端
cd frontend && npm run lint
cd frontend && npm run build
```

`npm run build` 执行 `tsc && vite build`，无需重复运行单独 type-check。

### 相关测试

```bash
# 后端：优先目标包，再按风险扩大
go test ./internal/service/... -v
go test ./internal/repository/... -v

# 前端单测
cd frontend && npm run test

# 关键流程 E2E（使用专用 mocked test server）
cd frontend && npm run test:e2e
cd frontend && npm run test:e2e:chromium
```

文档任务验证 Markdown 链接、目标路径、标题层级、重复内容、文件大小和 Git diff。

### 失败处理

1. 判断是否由本次修改导致。
2. 本次引入的问题必须修复并重跑。
3. 既有失败必须记录证据和影响，不能假装通过。
4. 不删除测试、不降低校验、不忽略警告。

## 步骤 13：测试报告

```text
测试报告：

执行：
- <命令>：通过 / 失败 / 阻塞

覆盖：
- <功能、模块、用例>

统计：
- 计划/执行/通过/失败/阻塞：<数量或不适用>
- 覆盖率：<数值或未采集>

发现的问题：
- <问题或无>

结论：
- 通过 / 有条件通过 / 不通过
```

不得编造覆盖率或测试数量。
