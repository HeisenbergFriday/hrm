# 阶段一：需求分析

## 步骤 1：识别需求意图

| 类型 | 优先上下文 |
|---|---|
| 新功能 | 对应模块文档；位置不明才读 PROJECT_MAP；跨模块再读 ARCHITECTURE |
| Bug | 报错、日志、失败测试、相关调用链和模块文档 |
| 重构 | ARCHITECTURE、CONVENTIONS、目标区域代码 |
| UI/样式 | DESIGN_SYSTEM、相关页面/组件；不默认读后端 |
| API/数据流 | ARCHITECTURE、模块文档、API 定义及调用方 |
| 数据库 | ARCHITECTURE、模块文档、model/migration 和依赖调用方 |
| 测试 | COMMANDS、CONVENTIONS、目标测试和被测代码 |
| 构建/部署 | COMMANDS、相关配置、CI/Docker/依赖文件 |
| 文档 | 目标文档及少量事实来源，不全量读代码 |

无法判断模块时才读 `.ai/PROJECT_MAP.md`；仍无法安全判断时提出一个简短澄清问题。

## 步骤 2：声明读取计划

任务开始输出：

```text
我判断这次任务属于：<类型>

预计需要读取：
- <文档/文件>

暂时不会读取：
- <无关目录>

原因：
<直接关联说明>
```

扩大范围前输出：

```text
当前缺少的信息：
- <信息>

准备继续读取：
- <文件/目录>

原因：
- <直接关联>
```

## 步骤 3：按需读取上下文

### 问题日志

开发、修 Bug、重构或工程配置变更前：

1. 读取 `docs/DEVELOPMENT_ISSUES.md` 顶部索引部分，不全文打开。
2. 用模块名或标签定位索引行。
3. 沿索引链接打开对应年度归档，只读取命中的条目正文。
4. 在修改计划引用适用约束。

### 设计规范

只有前端 UI、布局、组件、交互、状态展示、用户可见文案和无障碍变更才读取 `.ai/DESIGN_SYSTEM.md`。纯后端、数据库、脚本和部署任务不读取。

### 初始读取预算

- 根入口文档 1 份；
- 问题日志索引 + 相关条目；
- `.ai` 文档 0～2 份；
- 直接相关代码 1～5 份。

超出预算必须说明原因。禁止默认扫描 `frontend/src`、`internal`、`pages`、`components` 或全部 `.ai`。

## 步骤 4：需求确认与 PRD

### 触发

- 新功能；
- 复杂 Bug，需要确认正确行为；
- 跨模块功能；
- 数据库或公共契约变化。

简单样式、配置和纯文档更新可跳过。

### 最小需求说明

```text
需求来源：<用户/业务/Bug/技术优化>
目标：<解决的问题和价值>
用户故事：作为 <角色>，我想要 <能力>，以便 <价值>
验收标准：
- [ ] <标准>
影响范围：<模块/角色/数据/API>
优先级：P0 / P1 / P2
风险或待确认：<内容>
```

中大型功能在继续设计前应获得用户确认。禁止需求理解不清或没有验收标准就直接编码。
