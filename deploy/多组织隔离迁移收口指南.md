# 多组织隔离迁移收口指南

本文档用于 Phase 3B 之后的真实数据库收口。原则是：能唯一推导的历史数据才回填 `org_id`；不能唯一推导的记录进入 unresolved 清单人工处理；禁止把未知历史数据统一写入 `default`。

## 1. 备份

```bash
mysqldump -u root -p peopleops > backup_before_multitenant_contract.sql
```

## 2. 只读发现

```bash
go run ./tools/migrate_multitenant discover \
  --dsn "$DATABASE_DSN" \
  > multitenant-discover.json
```

重点检查：

- `summary.tenant_tables_missing_col` 必须为 0，表示 Phase 3B schema expand 已覆盖所有租户表。
- `summary.total_null_org_rows` 表示仍需回填或人工处理的历史记录数。
- 平台表如 `organizations`、`roles`、`permissions` 不应被强加 `org_id`。

## 3. 推导历史归属

```bash
go run ./tools/migrate_multitenant infer \
  --dsn "$DATABASE_DSN" \
  --out multitenant-infer.json
```

`infer` 会生成 manifest：

- `status=ready`：通过员工、部门或父表关系唯一推导出 `org_id`，可进入 apply。
- `status=unresolved`：没有候选组织或出现多个候选组织，必须人工确认。
- `status=skipped`：表结构不符合自动处理前提。

人工处理 unresolved 时，只允许基于员工、部门、审批、父子记录等证据补 `org_id`；无法证明归属的历史记录应保留 unresolved 并单独归档，不要随意写入默认组织。

## 4. 安全写入

确认 manifest 后执行：

```bash
go run ./tools/migrate_multitenant apply \
  --dsn "$DATABASE_DSN" \
  --manifest multitenant-infer.json \
  --confirm-apply
```

`apply` 只会更新 manifest 中 `status=ready` 且 `org_id` 非空的记录，并且 SQL 条件会要求目标行当前仍为 `NULL` 或空字符串，避免覆盖已人工修正的数据。

## 5. 验证

```bash
go run ./tools/migrate_multitenant verify \
  --dsn "$DATABASE_DSN"
```

必须通过的检查：

- 所有租户表存在 `org_id`。
- 所有租户表不存在 `NULL` 或空字符串 `org_id`。
- 有父子关系的表不存在父子 `org_id` 不一致。

## 6. 最终收口

先查看计划：

```bash
go run ./tools/migrate_multitenant contract \
  --dsn "$DATABASE_DSN"
```

确认计划无误后执行：

```bash
go run ./tools/migrate_multitenant contract \
  --dsn "$DATABASE_DSN" \
  --confirm-contract
```

`contract` 会在 `verify` 通过后执行收口计划，包括：

- 将仍为 nullable 的 `org_id` 改为 `NOT NULL`。
- 为缺少 `org_id` 索引的租户表补普通索引。
- 为关键表补复合唯一索引，例如 `users(org_id,user_id)`、`departments(org_id,department_id)`。

如果数据库已有旧的单列唯一索引导致 contract 失败，应先由 DBA 审核并替换为复合唯一索引，再重新运行 `contract`。

## 7. 上线前检查

```bash
go test ./...
npm run build
```

上线前再抽查：

```sql
SELECT org_id, COUNT(*) FROM users GROUP BY org_id;
SELECT org_id, COUNT(*) FROM departments GROUP BY org_id;
SELECT COUNT(*) FROM approvals WHERE org_id IS NULL OR org_id = '';
```

登录验证：

- 旧 Token 缺少 `org_id` 时必须失效。
- 登录必须选择组织。
- 普通接口不能通过 `org_id` 或 `target_org_id` 参数切换组织。
- 同名用户、同名部门在不同组织下只能访问各自组织数据。

## 8. 运维 CLI 组织约束

第五到第七阶段上线前，所有会读取或回写业务表的运维入口必须显式传入目标组织，禁止依赖默认组织或仅凭自增 ID 操作：

```bash
go run ./tools/ops/run_self_eval_reminders --org-id muteng --activity 123 --confirm-send
go run ./tools/ops/resync_comp_time --org-id muteng -ids 101,102
go run ./tools/resync_overtime_to_dingtalk --org-id muteng -dry-run
go run ./tools/set_comp_time_balance --org-id muteng -user example-user-id -year 2026 -minutes 480
go run ./tools/reset_vacation_quota --org-id muteng -leave-code example-leave-code
```

正式执行加班调休重放时仍需保留业务过滤条件：

```bash
go run ./tools/resync_overtime_to_dingtalk --org-id muteng -dry-run=false -user example-user-id
```

这些工具的查询和状态回写都必须同时带 `org_id` 与记录 ID 条件；如果传入的记录不属于该组织，应表现为查不到或更新不到，而不是跨组织处理。
